## 1. 背景与目标

本次改动用于提升智能体查询链路在异常、取消和重复操作场景下的可恢复性。主要目标如下：

- 防止供应商异常、状态初始化异常或会话持久化异常直接暴露底层错误。
- 保证已经创建的分析回合最终落为成功、失败或取消状态，不长期停留在 `running`。
- 让 SSE 客户端能够区分正常结束、业务错误和请求取消。
- 防止前端重复创建会话，并在初始化失败时向用户提供可见反馈。
- 保留 `request_id`、会话 ID 和回合 ID，便于根据请求定位服务端日志。

## 2. 后端请求链路

查询入口位于 `POST /api/v1/conversations/{conversation_id}/query`。请求处理分为准备阶段和流式图运行阶段。

### 2.1 请求准备阶段

后端先读取会话上下文并创建本轮 turn，然后创建图运行时和初始状态。准备阶段的异常按来源分类：

| 阶段 | 对外状态码 | 对外信息 | 回合处理 |
| --- | ---: | --- | --- |
| 会话不存在 | `404` | `Conversation was not found.` | 不创建回合或不修改已有回合 |
| LLM 未配置 | `503` | `LLM service is not configured.` | 标记回合失败 |
| 查询服务配置无效 | `503` | `The query service configuration is invalid.` | 标记回合失败 |
| 其他运行时异常 | `502` | `The NL2SQL agent could not complete the query.` | 标记回合失败 |

准备阶段的未知异常不会直接将 Python 异常文本返回给客户端，而是记录脱敏日志后返回统一错误。

### 2.2 图运行阶段

LangGraph 运行期间，后端通过 SSE 推送进度。每个进度事件会同步写入 assistant 消息的 `progress_json`，因此客户端刷新或跨设备恢复时仍能看到已产生的进度。

图运行结束后：

- 成功响应写入完整 `QueryResponse`，并将 assistant 消息状态更新为成功状态。
- 业务错误写入失败原因，并发送 `error` 事件。
- 客户端主动断开或任务被取消时，记录取消日志，并将回合收敛为取消错误。
- 回合收尾失败不会覆盖原始异常；收尾异常单独记录，避免异常处理再次抛出。

### 2.3 SSE 事件约定

流式接口使用标准 SSE 格式，每个事件包含 `event` 和 JSON 格式的 `data`：

| 事件 | 作用 | 主要字段 |
| --- | --- | --- |
| `start` | 标识查询开始 | `request_id`、回合信息 |
| `progress` | 推送节点或执行进度 | `request_id`、`node`、`message` |
| `complete` | 查询成功完成 | `request_id`、响应摘要 |
| `error` | 查询失败或取消 | `request_id`、`status_code`、`detail` |

客户端不应仅依赖 HTTP 状态码判断流式结果；建立连接成功后，应同时处理 SSE 的 `complete` 和 `error` 事件。

## 3. 错误处理策略

### 3.1 对外错误信息

对外错误信息遵循“可操作但不泄露底层细节”的原则：

- 配置类错误保留明确的修复方向，例如检查 LLM 配置。
- 未知异常统一使用通用提示，不返回供应商原始响应、堆栈或连接字符串。
- 前端将流式错误同步到当前 assistant 消息，并将消息状态改为失败，避免界面一直显示“正在处理”。

### 3.2 日志脱敏

服务端日志保留以下定位字段：

- `request_id`
- `conversation_id`
- `turn_id`
- 失败节点名称
- 异常类型和供应商状态码

异常摘要在写入日志前经过统一脱敏，并限制长度。连接 URL、credential、Bearer token 和常见 token 参数不会以原文写入日志。

### 3.3 会话状态收敛

`ConversationRepository.finish_turn` 负责同时更新 assistant 消息和 conversation turn。路由层通过安全收尾函数调用它：

1. 首先尝试保存失败或取消结果。
2. 如果持久化收尾再次失败，单独记录收尾异常。
3. 不让二次异常遮蔽原始查询失败。

该策略保证异常路径具有幂等、可观察的收尾行为。

## 4. 前端会话交互

前端 `createAgentConversationStore` 做了以下处理：

- 初始化时清空旧的初始化错误，并在加载失败时提供 `initializationError`。
- 创建新会话使用内部方法统一刷新列表和加载详情，避免初始化与手动创建逻辑分叉。
- 创建会话期间设置 `isBusy`，阻止重复点击造成并发创建。
- 发送问题前立即插入本地 user/assistant 占位消息，让流式进度有稳定的渲染目标。
- 收到最终响应后，用服务端的最终答案、状态和 `QueryResponse` 更新 assistant 消息。
- 流式请求失败时，将当前 assistant 消息标记为失败并展示错误，同时重新加载服务端会话详情。

浏览器仍不保存消息正文、查询结果或结果引用；刷新恢复以服务端会话数据为准。

## 5. 配置与安全边界

查询稳定性依赖以下配置约束：

- `MAX_ITERATIONS` 必须位于 `1` 到 `10`，限制模型自纠错调用次数。
- `QUERY_TIMEOUT_SECONDS` 必须为正数，避免查询无限等待。
- `RESULT_ROW_LIMIT` 必须为正数，限制返回结果规模。
- `INTENT_CONFIDENCE_THRESHOLD` 必须位于 `(0, 1]`。
- `CONVERSATION_CONTEXT_MAX_CHARS` 不得低于 `1000`，避免上下文配置过小导致会话语义丢失。

这些约束在启动或运行时配置校验阶段执行；部署前应同步检查 `.env.example` 与实际环境变量。
